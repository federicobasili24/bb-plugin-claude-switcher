# Claude Switcher su Windows — piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** claude-switcher fa su un server bb Windows esattamente quello che fa su macOS/Linux.

**Architecture:** Tutto ciò che dipende dalla piattaforma passa da un modulo nuovo `src/platform.ts` (funzioni pure con `platform` esplicito) e dagli IO di `src/node-io.ts`; la logica di reparto non si tocca. Su POSIX ogni funzione nuova restituisce byte per byte quello che il codice fa oggi.

**Tech Stack:** TypeScript (ESM), Node ≥ 22, Vitest, bb plugin SDK; Windows 11, Claude Code 2.1.322 (npm), bb 0.49.

**Spec:** `docs/superpowers/specs/2026-11-10-windows-design.md`

## Global Constraints

- Nessun cambiamento di comportamento su macOS/Linux: i test esistenti restano verdi **senza** cambiare le loro aspettative (solo `skipIf(win32)` per quelli che eseguono script `/bin/sh`).
- Nessun privilegio di amministratore richiesto; la Modalità sviluppatore può esserci o no (sul PC del collaudo c'è).
- Credenziali solo in `<configDir>\.credentials.json`; mai nei log.
- Collegamenti: mai cancellare, mai sovrascrivere, mai copiare.
- Fork `federicobasili24/bb-plugin-claude-switcher`, branch `windows` sopra `main` di monte; nessun tag; `dist/` non si ricostruisce su Windows (bb ricostruisce all'installazione da percorso).
- Repo pubblico: niente nomi di progetti, clienti o thread nei commit e nei documenti.
- Messaggi di commit in inglese come a monte; testo utente del plugin in inglese come a monte.

## Review Focus

1. `accountsDir` scritto con `/` su Windows (`C:/Users/x/.claude-accounts`) o con `\` finale → deve valere come quello nativo (test in Task 1).
2. Percorso con spazi (`C:\Users\Nome Cognome\…`) nell'helper `.cmd` e in `CLAUDE_CONFIG_DIR` → funziona (test in Task 4 e Task 2).
3. Cartella da collegare su un altro volume (`E:` vs `C:`) → la junction funziona fra volumi; il file `.jsonl` (EXDEV) va a symlink di file, e senza Modalità sviluppatore finisce in `errors`, mai copiato (test in Task 2).
4. `claudeCommand` lasciato a `claude` con solo `claude.cmd` di npm nel PATH → il login parte con `claude.exe` (test in Task 5).
5. `.credentials.json` bloccato un istante da Claude Code mentre il plugin lo rinnova → ritenta e riesce, senza lasciare `.tmp-*` (test in Task 3).

### Task 1: Percorsi (`src/platform.ts`)

**Files:**
- Create: `src/platform.ts`, `src/platform.test.ts`
- Modify: `src/accounts.ts` (`expandHome`, `normalizeDir`, controllo assoluto, join in `discoverAccounts`), `server.ts` (`plainPath` → import; `loginTarget`: `dir`, `own`, `configDir`; `account_login_start`: `shareFrom`), `src/node-io.ts` (`nodeAccountsIo` imposta `platform`)

**Interfaces:**
- Produces (tutte pure, `platform: NodeJS.Platform`):
  - `isAbsolutePath(p: string, platform): boolean` — POSIX: `p.startsWith("/")`; win32: `/^[A-Za-z]:[\\/]/` o `/^[\\/]{2}[^\\/]+[\\/][^\\/]+/` (UNC).
  - `expandHome(p: string, home: string, platform): string` — POSIX come oggi; win32 accetta anche `~\`.
  - `trimTrailingSeparators(p: string, platform): string` — POSIX: toglie `/` finali (lunghezza > 1, come oggi); win32: toglie `/` e `\` finali ma non dopo `C:` (`C:\` resta `C:\`).
  - `joinPath(dir: string, name: string, platform): string` — POSIX `${dir}/${name}`; win32 `${dir}\${name}` (dir già senza separatori finali).
  - `plainPath(p: string, platform): string` — POSIX: identico a `plainPath` di `server.ts` oggi; win32: minuscolo, separatori `/` e `\`, `.`/`..` risolti, risultato `c:/a/b` (la lettera d'unità è il primo segmento e `..` non la toglie).
  - `AccountsIo` guadagna `platform?: NodeJS.Platform` (assente = comportamento POSIX, così i test esistenti non cambiano).
- `expandHome` resta esportato da `src/accounts.ts` (lo importa `server.ts`) come `expandHome(path, home, platform = "linux")` che delega a `platform.ts`.

### Task 2: Collegamenti (junction, symlink, hard link)

**Files:**
- Modify: `src/node-io.ts` (`nodeLoginIo().link`, `nodeSessionsIo().symlink`), `src/login.ts` (`LoginIo.link` tipo, `prepare`)
- Test: `src/node-io.test.ts`, `src/login.test.ts`

**Interfaces:**
- `LoginIo.link(target, path): Promise<boolean | "hardlink">` — `"hardlink"` solo su win32 quando il symlink di file fallisce con `EPERM` e il hard link riesce.
- `prepare` mette in `linked` `"<entry> (hard link: Claude Code may unlink it when it rewrites the file)"` per un `"hardlink"`.
- `nodeLoginIo(platform = process.platform)` e `nodeSessionsIo(platform = process.platform)`: parametro per i test.
- Su win32: target cartella → `symlink(target, path, "junction")`; target file → `symlink(target, path, "file")`, e solo in `nodeLoginIo.link` su `EPERM` → `link(target, path)`. `nodeSessionsIo().symlink` per un file non ripiega (l'errore torna a `sessions.ts`, che lo mette in `errors`). POSIX invariato (`symlink(target, path)` senza tipo).

- [ ] **Step 1: test** (in `node-io.test.ts`, `describe.runIf(process.platform === "win32")("links on Windows")`, cartelle temporanee reali):
  - `nodeLoginIo().link(dir, path)` su una cartella → `true`, `lstat(path).isSymbolicLink()` true e `readdir(path)` vede il contenuto; seconda volta → `false` (EEXIST).
  - `nodeLoginIo().link(file, path)` su un file → `true` o `"hardlink"`; in entrambi i casi `readFile(path)` è il contenuto del file.
  - `nodeSessionsIo().symlink(dir, path)` → junction leggibile; su un `path` esistente → rifiuta con `EEXIST` e non tocca il contenuto.
  - in `login.test.ts`: un fake `LoginIo` il cui `link` risponde `"hardlink"` per `settings.json` → `onShared` riceve `"settings.json (hard link: Claude Code may unlink it when it rewrites the file)"` in `linked`.
